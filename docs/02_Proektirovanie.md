# 2 Проектирование автоматизированной системы поиска вакансий

## 2.1 Архитектура приложения

В качестве целевого архитектурного подхода была выбрана монолитная модульная архитектура с чётким разделением слоёв. Данный подход представляет собой построение приложения как единого целого с выделенными функциональными модулями, каждый из которых отвечает за отдельную бизнес-область: взаимодействие с платформой hh.ru, управление учётными записями, обработка вакансий, формирование сопроводительных писем и аналитика. Модули имеют чётко определённые границы ответственности и взаимодействуют через внутренние интерфейсы.

Выбор монолитной архитектуры обусловлен спецификой проекта: система предназначена для локального развёртывания или развёртывания на единичном сервере, где нет необходимости в независимом масштабировании отдельных компонентов. При этом внутри приложения выделены отдельные слои: слой представления (веб-интерфейс), слой бизнес-логики (обработка данных, интеграция с внешними сервисами) и слой доступа к данным (хранение вакансий, откликов, настроек). Такое разделение позволяет в дальнейшем при необходимости выделить отдельные компоненты в самостоятельные сервисы без существенной переработки кода.

Архитектура приложения включает следующие компоненты:

– **Веб-интерфейс (Dashboard)** — клиентская часть, реализованная на HTML, CSS и JavaScript. Предоставляет пользователю единую панель управления для настройки параметров поиска, мониторинга активности, управления учётными записями и анализа статистики.

– **Сервер приложений (FastAPI)** — основной backend-компонент, реализованный на языке Python с использованием фреймворка FastAPI. Обрабатывает HTTP-запросы от веб-интерфейса, управляет бизнес-логикой, обеспечивает интеграцию с внешними API и взаимодействие с базой данных.

– **Слой автоматизации (Worker)** — модуль фоновой обработки, отвечающий за выполнение запланированных задач: сбор вакансий по заданным критериям, отправку откликов, обновление статусов. Работает асинхронно и не блокирует основной сервер.

– **Интеграционный модуль hh.ru** — компонент, реализующий взаимодействие с платформой HeadHunter через публичное API и механизмы веб-скрапинга. Включает управление сессиями, обход ограничений на частоту запросов и обработку ответов сервера.

– **Модуль LLM-интеграции** — компонент для генерации персонализированных сопроводительных писем с использованием языковых моделей через API внешних провайдеров.

– **База данных (SQLite)** — встраиваемая реляционная база данных для хранения информации о вакансиях, отправленных откликах, учётных записях, шаблонах писем и журнале операций.

– **Telegram-бот** — дополнительный компонент для удалённого управления системой и получения уведомлений о выполненных задачах.

– **Прокси-сервер (Nginx)** — обеспечивает маршрутизацию внешних запросов к серверу приложений, раздачу статических файлов и терминацию SSL-соединений.

Взаимодействие между компонентами осуществляется следующим образом: пользователь через браузер открывает веб-интерфейс Dashboard, который загружает статические файлы через Nginx и устанавливает WebSocket-соединение с сервером FastAPI для получения обновлений в реальном времени. Сервер FastAPI обрабатывает запросы пользователя, обращается к базе данных SQLite и при необходимости инициирует фоновые задачи в слое Worker. Worker, в свою очередь, через интеграционный модуль hh.ru выполняет сбор вакансий или отправку откликов, а через модуль LLM-интеграции — генерирует сопроводительные письма. Результаты операций сохраняются в базе данных и передаются пользователю через WebSocket.

Система разворачивается в контейнерной среде Docker с использованием Docker Compose, что обеспечивает воспроизводимость окружения и упрощает процесс установки на различных платформах.

## 2.2 Проектирование структур данных

### 2.2.1 Концептуальная модель базы данных

Концептуальная модель данных используется для формализации структуры предметной области на раннем этапе проектирования. Такая модель отражает ключевые сущности и связи между ними.

Для автоматизированной системы поиска вакансий в качестве базовой была выбрана концептуальная модель, которая включает в себя следующие сущности: пользователь, учётная запись соискателя, вакансия, отклик, сопроводительное письмо (шаблон), резюме, настройки поиска, журнал операций. Данные сущности формируют базовый контур системы и отражают фактические действия пользователя: от настройки параметров поиска до анализа результатов отправленных откликов.

Табличное описание основных сущностей представлено в таблице 2.

**Таблица 2 – Табличное описание основных сущностей для концептуальной модели базы данных**

| Название сущности | Идентификатор сущности | Назначение сущности |
|:---|:---|:---|
| Пользователь | users | Хранит данные профиля пользователя системы |
| Учётная запись hh.ru | accounts | Содержит данные авторизации на платформе hh.ru (логин, токены, настройки) |
| Резюме | resumes | Хранит информацию о резюме пользователя, размещённом на hh.ru |
| Вакансия | vacancies | Содержит данные о найденных вакансиях (название, компания, требования, ссылка) |
| Отклик | applications | Хранит информацию об отправленных откликах (статус, дата, связь с вакансией) |
| Шаблон письма | letter_templates | Содержит тексты сопроводительных писем для различных категорий вакансий |
| Настройки поиска | search_configs | Хранит параметры поиска (ключевые слова, регион, зарплата, фильтры) |
| Журнал операций | logs | Фиксирует события системы (поиск, отправка отклика, ошибки) |

Концептуальная модель базы данных отражает следующие связи между сущностями:

– пользователь может иметь несколько учётных записей hh.ru (1:N);

– учётная запись связана с одним или несколькими резюме (1:N);

– вакансия может быть связана с несколькими откликами от разных учётных записей (1:N);

– отклик обязательно связан с одной вакансией и одной учётной записью (N:1);

– шаблон письма принадлежит пользователю и может использоваться для множества откликов (1:N);

– настройки поиска принадлежат конкретной учётной записи (1:1);

– журнал операций связан с учётной записью, над которой выполнялась операция (N:1).

### 2.2.2 Логическая модель базы данных

Логическая модель данных представляет собой развитие концептуальной модели и предназначена для формализации структуры реляционной базы данных на уровне сущностей, атрибутов, ключей, ограничений и связей. На данном этапе для каждой сущности уточняются состав полей и типы данных.

При проектировании реляционной базы данных автоматизированной системы поиска вакансий применялся предметно-ориентированный подход. В его рамках структура данных формировалась на основе доменных областей: управление пользователями, интеграция с hh.ru, обработка вакансий, управление откликами и письмами, сбор аналитики.

Основные таблицы логической модели включают:

**Таблица `users`** — хранение данных пользователей системы:

– `id` — первичный ключ, целое число;

– `username` — имя пользователя, текстовое поле;

– `password_hash` — хеш пароля, текстовое поле;

– `role` — роль пользователя (администратор, пользователь);

– `created_at` — дата создания записи.

**Таблица `accounts`** — учётные записи hh.ru:

– `id` — первичный ключ;

– `user_id` — внешний ключ на таблицу `users`;

– `hh_login` — логин на hh.ru;

– `hh_token` — токен авторизации;

– `resume_id` — идентификатор резюме на hh.ru;

– `is_active` — статус активности записи;

– `search_config` — сериализованные настройки поиска.

**Таблица `vacancies`** — информация о вакансиях:

– `id` — первичный ключ;

– `vacancy_id` — идентификатор вакансии на hh.ru;

– `title` — название вакансии;

– `company` — название компании;

– `salary_from`, `salary_to` — диапазон зарплаты;

– `experience` — требуемый опыт;

– `schedule` — тип занятости;

– `url` — ссылка на вакансию;

– `description` — описание вакансии;

– `found_at` — дата и время нахождения вакансии;

– `is_processed` — признак обработки вакансии.

**Таблица `applications`** — отправленные отклики:

– `id` — первичный ключ;

– `account_id` — внешний ключ на таблицу `accounts`;

– `vacancy_id` — внешний ключ на таблицу `vacancies`;

– `status` — статус отклика (отправлен, просмотрен, приглашение, отказ);

– `cover_letter` — текст сопроводительного письма;

– `sent_at` — дата и время отправки;

– `response_at` — дата и время получения ответа.

**Таблица `letter_templates`** — шаблоны сопроводительных писем:

– `id` — первичный ключ;

– `user_id` — внешний ключ на таблицу `users`;

– `name` — название шаблона;

– `text` — текст шаблона;

– `keywords` — ключевые слова для привязки к категориям вакансий.

**Таблица `logs`** — журнал операций:

– `id` — первичный ключ;

– `account_id` — внешний ключ на таблицу `accounts`;

– `level` — уровень события (info, warning, error, success);

– `message` — текст сообщения;

– `timestamp` — дата и время события.

Разработанная логическая модель обеспечивает наглядное представление структуры и взаимосвязей информационных сущностей системы. Использование внешних ключей обеспечивает ссылочную целостность данных, а типы полей соответствуют характеру хранимой информации.

## 2.3 Проектирование пользовательского интерфейса

При проектировании пользовательского интерфейса автоматизированной системы поиска вакансий необходимо учитывать функциональные требования системы и требования к удобству использования. Интерфейс должен обеспечивать быстрое и понятное выполнение ключевых пользовательских задач: настройка параметров поиска, мониторинг активности отправки откликов, управление учётными записями и анализ эффективности.

С учётом результатов сравнительного анализа существующих решений необходимо обеспечить следующие качества интерфейса: наглядное представление статусов операций, минимальное количество шагов для запуска поиска, удобную навигацию между разделами системы, адаптивность под различные устройства. Логика интерфейса строится вокруг основных ежедневных действий пользователя: запуск поиска вакансий, просмотр результатов, отправка откликов, анализ статистики.

При проектировании интерфейса были применены следующие решения по повышению удобства пользования:

– обеспечена визуальная иерархия экранов с выделением приоритетных данных (количество найденных вакансий, статус отправленных откликов, активность учётных записей);

– сокращено число шагов для базовых операций (запуск поиска, отправка отклика, просмотр статистики);

– обеспечено единообразие форм, кнопок и сценариев подтверждения действий;

– реализовано предупреждение ошибок ввода (валидация полей форм, проверка корректности настроек);

– обеспечена обратная связь системы при успешных и ошибочных действиях (уведомления, индикаторы статуса);

– обеспечена адаптивность интерфейса под разные размеры экрана.

Технически пользовательский интерфейс реализован как одностраничное веб-приложение (Single Page Application, SPA) на чистом JavaScript с использованием HTML и CSS. Архитектурный подход SPA предполагает, что пользователь работает в пределах одной загруженной HTML-страницы, а смена разделов выполняется за счёт динамического обновления представления без полной перезагрузки документа. Навигация по URL в таком приложении сохраняется, однако маршрутизация реализуется на стороне клиента.

Интерфейс системы организован по принципу левосторонней навигационной панели с основным рабочим пространством справа. Левая панель содержит логотип системы, переключатель разделов и индикатор статуса подключения. Основные разделы интерфейса включают:

– **Главная** — дашборд с ключевыми показателями: количество найденных вакансий, отправленных откликов, статистика по учётным записям, график активности;

– **Лог** — журнал операций системы с фильтрацией по уровню событий (информация, предупреждение, ошибка, успех) и по учётным записям;

– **Отклики** — список отправленных откликов с информацией о статусе, возможностью фильтрации и поиска;

– **Тесты** — раздел для управления тестовыми заданиями от работодателей;

– **База** — база данных собранных вакансий с возможностью фильтрации, сортировки и поиска;

– **HH Статус** — информация о состоянии интеграции с платформой hh.ru (доступность API, лимиты запросов);

– **Просмотры** — статистика просмотров резюме работодателями;

– **Отклик** — интерфейс для ручной отправки отклика на конкретную вакансию с выбором шаблона сопроводительного письма;

– **Настройки** — конфигурация системы: управление учётными записями hh.ru, настройки поиска, параметры LLM-интеграции, шаблоны писем.

Применение подхода SPA позволило сократить количество полных перезагрузок интерфейса, повысить отзывчивость системы и обеспечить более целостный пользовательский сценарий при переходе между разделами. Компонентный подход, реализованный на уровне JavaScript, предполагает декомпозицию интерфейса на автономные элементы: карточки вакансий, формы настроек, таблицы данных, элементы навигации и уведомления. Каждый компонент инкапсулирует собственную разметку, логику поведения и локальное состояние.

Для обеспечения современного и профессионального внешнего вида интерфейс выполнен в тёмной корпоративной цветовой схеме с акцентными цветами для индикации статусов. Использование CSS-переменных позволяет централизованно управлять цветовой палитрой, типографикой и отступами. Взаимодействие с сервером реализовано через WebSocket-соединение для получения обновлений в реальном времени и REST API для выполнения операций.

## 2.4 Проектирование программных средств

В ходе проектирования серверной части приложения была разработана структурная диаграмма компонентов системы в нотации UML. Диаграмма компонентов является структурной диаграммой, которая используется для формального представления архитектуры системы на уровне программных модулей, их интерфейсов и зависимостей. Такое представление позволяет заранее определить границы слоёв приложения, проверить согласованность архитектурных решений и снизить риск ошибок на этапе реализации.

Архитектура серверной части построена по принципу разделения ответственности (Separation of Concerns) и включает следующие ключевые модули:

– **Модуль веб-сервера (`web_app.py`)** — центральный компонент, реализованный на базе фреймворка FastAPI. Обеспечивает маршрутизацию HTTP-запросов, обработку WebSocket-соединений, валидацию входных данных и формирование ответов. Включает endpoints для управления учётными записями, запуска поиска, получения статистики, обработки настроек.

– **Модуль автоматизации (`hh_apply.py`)** — ядро бизнес-логики системы. Реализует алгоритмы сбора вакансий с платформы hh.ru, формирования и отправки откликов, управления сессиями учётных записей, обработки ограничений API. Включает механизмы обхода антиспам-защиты и управления частотой запросов.

– **Модуль интеграции с LLM** — компонент для взаимодействия с API языковых моделей (OpenAI, Anthropic и др.). Отвечает за генерацию персонализированных сопроводительных писем на основе описания вакансии и данных соискателя. Поддерживает конфигурацию нескольких провайдеров с механизмом fallback.

– **Модуль хранения данных** — слой доступа к базе данных SQLite. Реализует операции создания, чтения, обновления и удаления записей (CRUD) для всех сущностей системы. Включает механизмы миграции схемы базы данных и управления подключениями.

– **Модуль Telegram-интеграции** — компонент для взаимодействия с Telegram Bot API. Обеспечивает удалённое управление системой через команды бота и рассылку уведомлений о выполненных операциях.

– **Модуль планировщика задач** — компонент для управления фоновыми процессами: запуск поиска по расписанию, периодическое обновление статусов откликов, очистка устаревших данных.

Взаимодействие между модулями осуществляется через явно определённые интерфейсы. Модуль веб-сервера выступает в роли фасада, принимая запросы от клиентской части и делегируя их соответствующим модулям бизнес-логики. Модуль автоматизации не имеет прямой зависимости от веб-сервера и может функционировать в режиме командной строки, что обеспечивает гибкость развёртывания.

| LLM Connector | Интеграция с API языковых моделей, генерация сопроводительных писем |
| SQLite Manager | Управление подключениями к базе данных, выполнение CRUD-операций |
| Telegram Bot | Удалённое управление системой и уведомления через Telegram |
| Task Scheduler | Планирование и запуск фоновых задач по расписанию |
| Config Manager | Управление конфигурацией системы, валидация настроек |
| Logger | Централизованное логирование операций с разделением по уровням |

Спроектированная архитектура наглядно отражает структуру серверной части системы, состав её основных компонентов и характер их взаимодействия. Модульное разделение позволяет локализовать изменения при доработках и обеспечивает возможность тестирования отдельных компонентов независимо друг от друга.
